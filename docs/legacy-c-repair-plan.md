# 原 C 版网盘修复与复习设计

## 1. 目标

第一阶段以现有 C 版本为基线，在实验室 Linux 服务器上恢复构建和运行环境，按模块修复必须处理的 Bug，并通过实际代码修改重新熟悉 Linux 系统编程、网络编程、线程池、文件传输和 MySQL 交互。

阶段结束时应得到一个可构建、可部署、核心流程通过测试的 C 版本，为后续 C++ 重构提供稳定参照。

## 2. 范围

本阶段包含：

- 整理整个项目并使用私有 GitHub 仓库管理。
- 将源码同步到实验室服务器，在服务器上编译、运行和测试。
- 补齐数据库建表与初始化脚本、依赖说明、构建和启动说明。
- 按 `docs/legacy-c-bugs.md` 分批修复原 C 版问题。
- 每批修改前简要讲解 Bug 原理、涉及调用链和修复方法。
- 为修复结果提供与风险相称的编译、功能、异常和并发测试。

本阶段不进行 C++ 重构，也不引入 Redis、HTTP、JWT、Nginx、消息队列等后续技术栈；只有完成原版修复所必需的工程调整可以加入。

## 3. 仓库与环境模型

- 本地 `F:\study\net_disk` 是源码和文档主工作区。
- 私有 GitHub 仓库保存整个项目，包括源码、文档以及后续增加的 `sql/`、`scripts/` 和测试代码。
- 实验室服务器承担 Linux 编译、MySQL、运行、调试、内存检查和性能测试。
- 大型测试文件、编译产物、运行数据、数据库密码、服务器地址和密钥不进入 Git。
- 大型测试文件在服务器上按需生成。
- 配置文件只保存不含秘密的模板；真实配置留在服务器，并由 `.gitignore` 排除。

## 4. 模块顺序

### 4.1 工程基线与迁移

整理仓库和忽略规则，恢复客户端与服务端构建，补齐依赖、配置模板和数据库初始化脚本，在服务器上跑通最小启动流程。

### 4.2 启动流程、网络协议与 I/O

结合客户端和服务端入口、TCP 建连、`epoll`、命令分发和数据收发，处理长度校验、断线语义、短读短写、大文件长度、阻塞主循环以及协议布局和字节序等问题。

### 4.3 线程池、事件循环与连接生命周期

结合任务队列、工作线程、超时轮、连接容器和退出流程，处理数组越界、链表悬空、共享数据竞争、超时推进、资源释放和优雅退出等问题。

### 4.4 注册登录、鉴权与数据库

结合注册登录、密码处理、Token、SQL 执行和连接状态，处理 SQL 注入、权限配置、认证门禁、可预测凭据、密码重放和输入安全等问题。

### 4.5 文件传输与元数据一致性

结合上传、下载、秒传、断点续传、虚拟目录和引用计数，处理路径穿越、零长度文件、半文件、脏元数据、哈希校验、同名文件和并发一致性等问题。

### 4.6 完整回归与说明

统一验证注册、登录、目录操作、上传、下载、秒传、异常断线、并发和退出流程，补齐部署说明、架构说明和修复记录。

## 5. 单批修复流程

每次选择一小组调用链相近的 Bug，采用以下流程：

1. AI 简要说明 Bug 原理、影响、代码位置和修复思路。
2. 直接修改代码，不要求用户手工复现原 Bug。
3. 在短期修复分支上提交并推送修改。
4. 服务器拉取分支，执行编译和对应测试。
5. 若测试失败，在同一分支继续修复并重新测试。
6. 测试通过后合并到 `main`，并总结本批涉及的知识点。

不要求一次只修一个 Bug；同一调用链、能够共同验证的问题可以作为一批处理。`main` 只接收已经在服务器上通过对应验证的修改。

## 6. 错误处理与测试原则

- 修改前先确认函数返回值、资源所有权、连接状态和线程边界，避免只修表面现象。
- 网络和磁盘 I/O 必须覆盖短读、短写、`EINTR`、断线和失败路径。
- 数据库与文件系统的组合操作必须明确失败恢复方式，不能假设两者能够组成单个原子事务。
- 测试以风险为依据：普通逻辑使用功能测试，内存与资源问题使用动态检查，并发与状态问题增加并发或异常流程测试。
- 未通过服务器验证的修复不得合并到 `main`。

## 7. 完成标准

- 客户端和服务端可在目标 Linux 服务器上按文档构建和启动。
- 数据库可由仓库内脚本初始化，秘密信息不进入版本库。
- 必须修复清单中的项目都有对应代码修改和验证记录。
- 注册、登录、目录操作、上传、下载、秒传和退出等核心流程通过回归测试。
- 编译告警、内存错误、资源泄漏和主要并发问题达到清单约定的验收标准。
	- 仓库具备清晰的部署说明、架构说明、Bug 修复历史和可供 C++ 重构参考的稳定 C 基线。
