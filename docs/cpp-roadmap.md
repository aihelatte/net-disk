# C++ 重构路线

## 1. 文档目的

本文记录网盘项目从原 C 版本演进到简历项目的三层 C++ 重构纲领。当前只确定各层目标、边界和选择原则，不提前确定具体类设计、模块顺序、系统功能或技术栈接入顺序。

具体实施应在原 C 版本按照 [legacy-c-repair-plan.md](legacy-c-repair-plan.md) 完成修复并形成稳定基线后开始。

## 2. 总体路线

项目按照以下顺序演进：

1. 修复并重新熟悉原 C 版本。
2. 完成第一层 C++ 等价语言重构。
3. 完成第二层系统能力增强。
4. 完成第三层后端技术栈扩展。

三个层次必须分开推进，使语言学习、系统能力和工程技术栈各自具有清晰目标。

## 3. 第一层：C++ 等价语言重构

### 3.1 目标

以修复后的 C 版本为功能基线，将项目改写为现代 C++，重点学习和使用 C++20。

### 3.2 边界

- 保持原有业务功能、通信协议、数据库结构和整体运行流程不变。
- 不在这一层增加新的系统功能或外部技术栈。
- 内部实现采用合理的 C++ 写法，不进行机械的逐行语法替换。
- 可以使用类与对象、封装、RAII、智能指针、STL、移动语义、Lambda、C++ 并发工具和 CMake 表达原有逻辑。
- 具体由谁编写哪些代码，等真正开始重构时再确定；总体采用人机混合学习方式。

### 3.3 结果

第一层结束后，应得到一个与稳定 C 版功能等价、能够独立构建和测试的 C++ 基线版本。

## 4. 第二层：系统能力增强

### 4.1 宗旨

第二层不是重新改写第一层已有内容，也不是单纯整理现有架构。它是在 C++ 基线之上，寻找项目尚未具备但值得新增的系统能力，并将其作为新功能加入项目。

新增能力主要从以下六个方向寻找：

1. 网络模型。
2. 并发模型。
3. 连接与可靠性。
4. 文件与存储。
5. 数据结构与算法。
6. 性能与验证。

六个方向是候选范围，不是必须全部修改的任务清单。具体新增哪些功能，等第一层完成后根据项目缺口重新评估。

### 4.2 加分项选择原则

候选功能应满足：

- 对网盘业务有实际作用。
- 属于经典、通用的系统或后端知识，具有面试价值。
- 是原项目缺失的新能力，而不是第一层语言重构的重复工作。
- 实现难度和开发成本合理。
- 可以清楚解释原理、使用场景和设计取舍。
- 可以通过功能测试或性能数据证明价值。
- 主要体现 C++、操作系统、网络编程、并发或数据结构能力，而不是依赖外部技术栈堆砌。

线程池属于这类加分项的典型代表。原项目已经具有线程池，因此未来应寻找其他类似线程池、同时又是当前项目所缺失的经典能力。

## 5. 第三层：后端技术栈扩展

### 5.1 宗旨

第三层按照项目当时的实际业务和工程需求，从 [technology-stack.md](technology-stack.md) 中逐项选择并引入主流后端技术栈。

### 5.2 引入原则

- 一次只加入一个技术栈，或一组无法合理拆分的强相关技术栈。
- 每项技术必须解决明确的业务或工程问题。
- 引入时同步修改业务代码、配置、测试和文档。
- 优先选择主流、通用、面试常问的技术。
- 没有实际用途的技术暂不加入。
- 不提前锁定完整接入顺序，实施时根据依赖关系和项目需求逐项决定。
- 最终必须能够说明为什么使用、解决了什么问题以及产生了什么效果。

Redis、JWT、TLS、Nginx、Docker、日志和监控等必选候选，以及 gRPC、RabbitMQ、MinIO 等条件候选，均按照以上原则分别评估，不一次性全部加入。

## 6. 三层边界

- 第一层解决“如何用现代 C++ 表达现有项目”。
- 第二层解决“还可以增加哪些有价值的系统能力”。
- 第三层解决“如何逐项接入主流后端工程技术栈”。

如果一项工作同时涉及多个层次，应先完成较低层的稳定版本，再在其上单独加入高层变化，保证每次演进都能够理解、测试和说明。
