# 网盘项目技术栈规划

## 1. 文档目的

本文记录网盘项目在原 C 版本修复、C++ 重构和后续包装过程中计划学习与使用的技术栈。

项目目标是作为面向通用后端/服务端实习的重点简历项目。技术选型遵循以下原则：

- 属于主流后端知识，具有较高的面试讨论价值；
- 能解决网盘项目中的真实问题，而不是单纯堆砌名词；
- 引入后能够通过功能、测试、指标或部署结果证明其价值；
- 每项技术都需要理解原理、使用场景、替代方案和关键取舍。

本文是阶段性规划。标记为“工具待选”的能力必须实现，但具体库或平台将在架构和运行环境确定后再选择。

## 2. 必选技术栈

### 2.1 C++20

- **状态：** 已确定
- **用途：** 重构客户端和服务端的核心代码。
- **重点内容：** RAII、智能指针、STL、移动语义、对象生命周期、模板、并发和错误处理。
- **项目要求：** C++ 版本不能只是把 C 函数改成类，而要通过资源所有权和模块边界体现现代 C++ 设计。

### 2.2 CMake

- **状态：** 已确定
- **用途：** 管理客户端、服务端、公共库、测试及第三方依赖的构建。
- **重点内容：** Target、依赖传播、构建类型、安装规则、测试集成和跨环境构建。
- **项目要求：** 支持 Debug、Release 和 Sanitizer 构建，并能在干净环境中复现。

### 2.3 GCC 与 Clang

- **状态：** 已确定
- **用途：** 在 Linux 服务器上编译、诊断和验证项目。
- **重点内容：** 编译警告、优化级别、调试符号、Sanitizer 和静态分析。
- **项目要求：** 核心代码至少能通过 GCC 构建；条件允许时增加 Clang 构建验证。

### 2.4 Linux 系统编程

- **状态：** 已确定
- **用途：** 构成文件服务、进程、线程、信号、定时器和资源管理的基础。
- **重点内容：** 文件描述符、文件 I/O、`mmap`、信号、进程/线程、系统调用错误处理和资源限制。
- **项目要求：** 每个系统调用都必须处理返回值、错误、资源释放和边界条件。

### 2.5 TCP/IP 与 Socket 网络编程

- **状态：** 已确定
- **用途：** 支撑客户端与服务端通信及文件传输。
- **重点内容：** TCP 字节流、粘包/拆包、半包、短写/短读、网络字节序、超时、断线、背压和连接生命周期。
- **项目要求：** 建立有版本、长度上限和明确错误语义的协议，统一可靠收发接口。

### 2.6 `epoll` 与 Reactor

- **状态：** 已确定
- **用途：** 实现 Linux 服务端的高并发连接管理。
- **重点内容：** I/O 多路复用、LT/ET、非阻塞 I/O、事件循环、连接状态机和 Reactor 模式。
- **项目要求：** 能解释事件循环与工作线程的职责边界，并通过并发测试验证。

### 2.7 线程池与任务调度

- **状态：** 已确定
- **用途：** 将耗时的文件和数据库任务与网络事件循环分离。
- **重点内容：** 任务队列、互斥量、条件变量、任务所有权、优雅退出、队列上限和过载保护。
- **项目要求：** 消除共享命令缓冲区等数据竞争，并能够观测队列长度和任务耗时。

### 2.8 HTTP 与 REST API

- **状态：** 已确定
- **用途：** 为 Web 页面和通用客户端提供标准接口。
- **重点内容：** HTTP 方法、状态码、Header、Keep-Alive、幂等性、分页、Range、错误响应和 API 版本。
- **项目要求：** 用户、目录、文件元数据、上传和下载提供清晰的 REST 接口；底层私有 TCP 协议是否保留将在架构设计时决定。

### 2.9 JSON

- **状态：** 已确定
- **用途：** 作为 HTTP API 的主要请求和响应格式。
- **重点内容：** 序列化、反序列化、字段校验、兼容性和错误处理。
- **项目要求：** 只用于控制和元数据，不使用 JSON 直接承载大文件内容。

### 2.10 MySQL

- **状态：** 已确定
- **用途：** 保存用户、目录树、文件元数据、引用关系和上传任务。
- **重点内容：** 表设计、索引、事务、隔离级别、MVCC、预编译 SQL、连接池、唯一约束和 `EXPLAIN`。
- **项目要求：** 提供数据库建表/迁移脚本；文件与元数据操作具备明确的一致性策略。

### 2.11 Redis

- **状态：** 已确定
- **用途：** 缓存热点元数据、登录限流、会话/令牌状态和上传任务状态。
- **重点内容：** 常用数据结构、过期策略、持久化、缓存一致性以及缓存穿透、击穿和雪崩。
- **项目要求：** 每个 Redis 用途都必须说明为什么不能只使用进程内存或 MySQL，并设计缓存失效策略。

### 2.12 JWT

- **状态：** 已确定
- **用途：** 实现无状态的访问令牌。
- **重点内容：** Header/Payload/Signature、签名验证、过期时间、密钥管理、令牌撤销和重放风险。
- **项目要求：** Token 只能由服务端签发，密钥不得发送给客户端或硬编码在源码中。

### 2.13 Access Token 与 Refresh Token

- **状态：** 已确定
- **用途：** 在安全性和用户会话体验之间取得平衡。
- **重点内容：** 短期访问令牌、长期刷新令牌、轮换、撤销、Redis 会话状态和退出登录。
- **项目要求：** 明确刷新流程、异常处理和令牌泄露后的失效方式。

### 2.14 密码安全

- **状态：** 已确定
- **候选方案：** Argon2id 或 bcrypt，具体库待选。
- **用途：** 安全存储和验证用户密码。
- **重点内容：** Salt、计算成本、离线破解、恒定时间比较和登录限流。
- **项目要求：** 不传输可直接重放的密码散列，不自行设计密码算法。

### 2.15 TLS 与 OpenSSL

- **状态：** 已确定
- **用途：** 保护登录凭据、令牌、文件内容和 API 通信。
- **重点内容：** TLS 基础、证书、握手、加密边界和证书验证。
- **项目要求：** 可由 Nginx 终止 TLS；是否在 C++ 服务内部直接使用 OpenSSL 将在架构设计时决定。

### 2.16 Nginx

- **状态：** 已确定
- **用途：** HTTPS 终止、反向代理、静态页面、请求限制和后续负载均衡。
- **重点内容：** 反向代理、超时、上传大小、限流、Header 转发和负载均衡策略。
- **项目要求：** 提供可复现的 Nginx 配置，并解释网关层与业务服务的职责边界。

### 2.17 Docker

- **状态：** 已确定
- **用途：** 固化服务端及其依赖的运行环境。
- **重点内容：** 镜像、容器、网络、卷、环境变量、健康检查和最小权限运行。
- **项目要求：** 镜像中不得写入数据库密码、JWT 密钥或测试数据。

### 2.18 Docker Compose

- **状态：** 已确定
- **用途：** 一条命令启动网盘服务、MySQL、Redis、Nginx和监控组件。
- **重点内容：** 服务依赖、网络、持久化卷、健康检查和配置注入。
- **项目要求：** 在干净 Linux 环境中能够按 README 完成部署。

### 2.19 自动化测试

- **状态：** 能力已确定，工具待选
- **候选工具：** GoogleTest、Catch2，以及自定义集成测试脚本。
- **用途：** 验证协议、目录、上传下载、断点续传、并发和故障恢复。
- **重点内容：** 单元测试、集成测试、回归测试、异常路径和可重复测试数据。
- **项目要求：** 原 C 版每个必修 Bug 都有复现和回归验证；C++ 版核心模块可以独立测试。

### 2.20 动态与静态代码检查

- **状态：** 已确定，工具组合待选
- **候选工具：** AddressSanitizer、ThreadSanitizer、UndefinedBehaviorSanitizer、Valgrind、Clang-Tidy 和 Cppcheck。
- **用途：** 发现越界、UAF、数据竞争、未定义行为、资源泄漏和代码质量问题。
- **项目要求：** 形成固定检查命令，并在关键阶段保存验证结果。

### 2.21 性能测试与分析

- **状态：** 已确定，工具待选
- **候选工具：** 自定义压测客户端、wrk、ApacheBench、Google Benchmark、`perf`。
- **用途：** 验证并发连接、吞吐量、延迟、CPU、内存和线程池行为。
- **项目要求：** 简历上的性能描述必须来自可复现实验，而不是使用“高性能”等空泛措辞。

### 2.22 日志

- **状态：** 能力已确定，工具待选
- **候选工具：** spdlog、Boost.Log 或自定义轻量封装。
- **用途：** 记录请求、错误、登录、安全事件、文件任务和关键耗时。
- **重点内容：** 日志级别、结构化字段、请求 ID、轮转、脱敏和异步日志。
- **项目要求：** 禁止记录密码、完整 Token 和敏感文件内容。

### 2.23 指标与监控

- **状态：** 能力已确定，工具待选
- **候选工具：** Prometheus、Grafana 或更轻量的指标展示方案。
- **用途：** 观测请求量、活跃连接、错误率、延迟、线程池队列和文件吞吐量。
- **项目要求：** 指标必须帮助定位实际问题；是否完整引入 Prometheus/Grafana将在后期根据工作量决定。

### 2.24 Git

- **状态：** 已确定
- **用途：** 管理原 C 修复、C++ 重构、文档和实验记录。
- **重点内容：** 分支、提交、代码审查、版本标签和可追踪的重构历史。
- **项目要求：** 巨型测试文件、密钥、构建产物和运行数据不得提交到仓库。

### 2.25 CI/CD

- **状态：** 能力已确定，平台待选
- **候选平台：** GitHub Actions、GitLab CI 或实验室服务器上的自动化脚本。
- **用途：** 自动构建、测试、静态检查和生成镜像。
- **项目要求：** 至少实现持续集成；自动部署是否加入将在服务器使用方式确定后决定。

## 3. 推荐但必须有业务理由的技术栈

### 3.1 gRPC

- **状态：** 候选，暂不进入核心版本
- **适用条件：** 项目拆分为元数据服务、文件服务或多个存储节点，需要内部 RPC 通信。
- **学习价值：** RPC、IDL、超时、状态码、重试、流式传输和服务边界。
- **限制：** 单体服务中强行加入 gRPC 只会增加复杂度。

### 3.2 Protocol Buffers

- **状态：** 候选，通常与 gRPC 一起评估
- **适用条件：** 需要稳定、紧凑、跨语言的内部消息格式。
- **学习价值：** Schema、字段编号、向前/向后兼容和代码生成。
- **限制：** 不替代对 HTTP/JSON 和底层 TCP 协议的理解。

### 3.3 RabbitMQ

- **状态：** 候选，暂不进入核心版本
- **适用条件：** 出现文件校验、垃圾清理、通知、缩略图或其他可异步执行的任务。
- **学习价值：** 消息队列、确认、重试、死信、幂等、顺序和削峰。
- **限制：** 没有可靠异步任务时不为简历堆栈而引入。

### 3.4 MinIO

- **状态：** 待斟酌，不进入当前主线
- **用途：** 提供自托管、兼容 Amazon S3 API 的对象存储。
- **适用条件：** 后期希望将本地磁盘和 S3 兼容对象存储设计成可切换的存储后端。
- **学习价值：** 对象存储、Bucket、Object、预签名 URL 和存储适配层。
- **限制：** 它会接管核心文件存储能力，过早加入会削弱本项目对文件传输和存储实现的展示。

### 3.5 Amazon S3 API

- **状态：** 概念和接口候选
- **适用条件：** 设计通用对象存储适配器，或需要兼容云对象存储。
- **学习价值：** 对象存储语义、分段上传、ETag、预签名访问和生命周期管理。
- **限制：** 当前阶段不要求接入真实公有云服务。

### 3.6 React

- **状态：** 可选前端方案，用户已有经验
- **用途：** 制作登录、目录浏览、上传下载、进度和分享页面。
- **项目定位：** 只负责项目演示和 API 使用验证，不作为主要考察重点。
- **实施原则：** 可使用 AI 提高开发效率，但需要能够解释页面状态、接口和上传流程。

### 3.7 Vue

- **状态：** 可选前端方案，和 React 二选一
- **用途：** 与 React 相同，用于轻量可视化演示。
- **项目定位：** 不同时维护两套前端，优先选择用户更熟悉、实现更快的一种。

## 4. 当前暂缓的技术

以下技术并非不重要，但在单机或早期版本中缺少足够业务理由，暂不加入：

- Kubernetes；
- Kafka；
- Elasticsearch；
- 服务注册与配置中心；
- 复杂微服务拆分；
- 分布式共识协议；
- 为展示而设计的分布式锁。

只有当项目规模和架构自然产生对应问题时，才重新评估这些技术。

## 5. 选型与验收规则

每项技术正式进入项目前，需要回答：

1. 它解决了什么具体问题？
2. 不使用它时的方案是什么？
3. 为什么选择它而不是其他替代方案？
4. 引入后增加了哪些复杂度和故障点？
5. 如何通过测试、日志、指标或性能数据证明它有效？
6. 面试中能否独立解释其核心原理、使用边界和项目取舍？

无法回答以上问题的技术，不写入简历的“已使用技术栈”。
